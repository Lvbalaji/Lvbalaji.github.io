# Server-Side Template Injection: Understanding the Mechanics

Server-Side Template Injection (SSTI) is often mistaken for Cross-Site Scripting (XSS) by beginners because they both involve injecting characters into a web page. However, the difference in impact is catastrophic. While XSS targets the *client* (browser), SSTI targets the *server*.

If you can successfully exploit SSTI, you are often just one payload away from **Remote Code Execution (RCE)** and full server compromise.

---

## 🔸 1. What is a Template Engine?

Modern web applications rarely use static HTML files. Instead, they use **Template Engines** to generate HTML dynamically. A template engine takes a static "skeleton" page (the template) and combines it with dynamic data (the context) to produce the final HTML response.

**Common Engines:**
* **Python:** Jinja2, Mako, Tornado
* **PHP:** Twig, Smarty
* **Java:** Freemarker, Velocity
* **Node.js:** Pug (Jade), EJS



---

## 🧨 2. The Vulnerability: Code vs. Data

SSTI vulnerabilities do **not** exist because template engines are inherently insecure. They exist because of **insecure implementation** by the developer.

The core flaw lies in how the user's input is handled before it reaches the engine.

### The Fatal Mistake: Concatenation
The vulnerability occurs when user-supplied input is **concatenated** directly into the template string *before* the engine renders it. This forces the engine to interpret the user's input as **code/syntax** rather than just text.

**❌ Insecure Implementation (Python/Jinja2 Example):**
```
# The developer mixes user input directly into the template CODE
user_input = request.args.get('name')
template = f"<h1>Hello {user_input}!</h1>" 
return render_template_string(template)
```

_If the user inputs `{{ 7*7 }}`, the server renders `Hello 49!` because `{{ }}` is valid code in Jinja2._

**✅ Secure Implementation:**


```
# The template is static. Input is passed as separate DATA.
template = "<h1>Hello {{ user }}!</h1>"
return render_template_string(template, user=user_input)
```

_If the user inputs `{{ 7*7 }}`, the server renders `Hello {{ 7*7 }}!` because the engine treats it as a plain string._

---

## 🧠 3. The Impact: Why is it Critical?

SSTI is a **Server-Side** vulnerability. Unlike XSS, which executes JavaScript in a victim's browser, SSTI executes code on the backend server.

**The Escalation Path:**

1. **Template Logic:** Attacker executes math (`7*7=49`).
    
2. **Object Access:** Attacker accesses internal application objects.
    
3. **Sandbox Escape:** Attacker escapes the template environment restrictions.
    
4. **RCE:** Attacker imports OS modules (`os`, `subprocess`) and executes shell commands (`ls`, `whoami`, `cat /etc/passwd`).
    

---

## 🧩 4. Detection & Identification

Before we can exploit, we must identify _which_ engine is running. Different engines use different syntax.

### Phase 1: The Polyglot Fuzz

To detect if input is being evaluated, we use a "polyglot" payload containing special characters used by multiple engines:

   ${{<%[%'"}}%

If the server returns an error (500) or renders the input strangely, it is likely vulnerable.

### Phase 2: The Decision Tree

Once vulnerability is suspected, we use mathematical operations to fingerprint the engine.

|**Payload**|**Output**|**Potential Engine**|**Why?**|
|---|---|---|---|
|`{{ 7*7 }}`|`49`|Jinja2, Twig|Basic expression evaluation.|
|`{{ 7*'7' }}`|`7777777`|**Jinja2 (Python)**|Python repeats the string 7 times.|
|`{{ 7*'7' }}`|`49`|**Twig (PHP)**|PHP coerces the string '7' to an integer and multiplies.|
|`#{ 7*7 }`|`49`|**Pug (Node.js)**|Uses `#{}` for interpolation.|
|`{'a'\|upper}`|`A`|**Smarty (PHP)**|Smarty syntax for filters.|

## 🛠️ 5. Attack Mechanics: The "Magic" of Introspection

How do we go from `{{ 7*7 }}` to `RCE`? We use the language's internal introspection capabilities to "climb" out of the template and access the operating system.

### 🐍 Python (Jinja2) Mechanics

Jinja2 is sandboxed. It doesn't let you just write `import os`. However, Python allows objects to look at their own type and their parents.

**The MRO Chain Strategy:**

1. **Start:** `""` (An empty string).
    
2. **Type:** `"".__class__` -> `<class 'str'>` (We are now accessing the Class definition).
    
3. **MRO:** `"".__class__.__mro__[1]` -> `<class 'object'>` (We walked up the "Method Resolution Order" to find the Root Object of Python).
    
4. **Subclasses:** `...__subclasses__()` -> This lists **every class** loaded in the current Python runtime.
    
5. **Hunt:** We look through that list for a dangerous class (gadget) like `subprocess.Popen` or `os._wrap_close`.
    
6. **Execute:** We instantiate that class to run shell commands.
    

**The Payload:**

```
{{ ''.__class__.__mro__[1].__subclasses__()[401]("whoami", shell=True, stdout=-1).communicate() }}
```

_(Note: The index `[401]` changes depending on the application environment)_.

### 🟢 Node.js (Pug) Mechanics

Node.js is less about inheritance and more about accessing the global scope.

We aim to access the global.process object to require the child_process module.

**The Payload:**

JavaScript

```
#{root.process.mainModule.require('child_process').spawnSync('ls', ['-lah']).stdout}
```

_Crucial Detail:_ `spawnSync` requires arguments to be passed as an **array** (`['-lah']`), not a string, or the command will fail.

### 🐘 PHP (Smarty) Mechanics

Smarty is often less sandboxed. It allows the execution of PHP functions directly within the syntax.

**The Payload:**

```
{system("ls")}
```

This directly calls the PHP `system()` function to execute the command.

## 🛡️ 6. Remediation & Defense Strategies

SSTI is 100% preventable by following secure coding practices.

### 1️⃣ Never Concatenate Input

This is the golden rule. Never build templates by joining strings with user input. Always use the engine's built-in context mechanism to pass variables.

1. **Bad:** `render_string("<h1>" + user_input + "</h1>")`
    
2. **Good:** `render_string("<h1>{{ name }}</h1>", name=user_input)`.
  

### 2️⃣ Input Sanitization (Defense in Depth)

If you must allow users to submit template-like data, implement a strict **whitelist**. Only allow alphanumeric characters and specific safe symbols. Strip out characters like `{{`, `}}`, `[`, `]`, `_`, and `%`.

### 3️⃣ Sandboxing

Ensure your template engine is running in a hardened sandbox environment. Remove dangerous modules/functions/classes (like `subprocess`, `os`, `exec`) from the template's global scope.

## ❓ 7. Interview Corner: Common FAQs (Pentest & AppSec)

If you are interviewing for a security role, expect these questions on SSTI.

### Q1: What is the main difference between XSS and SSTI?

**Answer:**

1. **XSS (Client-Side):** The payload is executed by the victim's _browser_. The impact is usually session hijacking or client-side defacement.
    
2. **SSTI (Server-Side):** The payload is executed by the _web server_ during the page rendering process. The impact is Remote Code Execution (RCE) and full server compromise.
    

### Q2: How do you differentiate between Jinja2 (Python) and Twig (PHP) during detection?

Answer:

I would use the payload {{ 7*'7' }}.

1. **Jinja2 (Python):** Strings are multiplied/repeated. Result: `7777777`.
    
2. **Twig (PHP):** Strings are loosely typed and converted to integers for math. Result: `49`.
    

### Q3: You found SSTI, but you can't figure out the correct index for `subprocess.Popen` in Jinja2. What do you do?

Answer:

Since the index changes based on imports, I would write a small script (or use a Burp Intruder attack) to fuzz the index number (e.g., from 0 to 500) inside the payload ...__subclasses__()[§INDEX§].... I would look for an error message or output that indicates I hit a class that accepts shell arguments.

### Q4: Why does `check_output('ls -lah')` fail in a Python SSTI payload?

Answer:

The subprocess.check_output (and similar functions) expects the command and arguments to be passed as a list of strings, not a single string with spaces. It treats "ls -lah" as a single executable name (which doesn't exist). The correct format is ['ls', '-lah'].

### Q5: Can you have SSTI without RCE?

Answer:

Yes. If the template engine is running in a robustly sandboxed environment (e.g., specific Python capabilities dropped, restricted namespaces), you might achieve "read-only" access to internal objects or environment variables but fail to execute system commands. However, reading environment variables often leaks API keys or database credentials, which leads to compromise anyway.

### Q6: What does the code `"".__class__.__mro__[1]` actually do in a Python payload?

Answer:

It performs object introspection to break out of the string context. "".__class__ accesses the String class. .__mro__[1] (Method Resolution Order) climbs up the inheritance tree to access the object class, which is the root of all classes in Python. From the object class, we can then list all subclasses to find a dangerous module like subprocess.

### Q7: If you see the output `Hello {{ 7*7 }}` (literally), is it vulnerable?

Answer:

No. This indicates that the server is treating the input as plain text/data, which is the secure way to handle templates. The vulnerability only exists if the server evaluates the expression and returns Hello 49.

### Q8: How can you exploit SSTI in Node.js (Pug/Jade) if `require` is blocked?

Answer:

You can try to access the process global object via root.process or global.process. From there, you can access mainModule and attempt to dynamically load child_process to execute system commands like spawnSync.

### Q9: What is the risk of using `render_template_string` in Flask?

Answer:

render_template_string allows rendering a string as a template. If a developer passes user-controlled input directly into this function without passing it as a named variable (context), it leads directly to SSTI. The secure alternative for files is render_template, or passing variables as arguments: render_template_string("{{ var }}", var=user_input).

### Q10: Are there automated tools for SSTI detection?

Answer:

Yes, tools like Tplmap (and its successor SSTImap) are designed to automate the detection and exploitation of SSTI. They can fingerprint the engine, identify the injection point, and attempt to provide a shell interface automatically.

## 🎭 8. Scenario-Based Questions

### 🎭 Scenario 1: The "Blind" Email

Context: You have a profile setting where you can update your "Display Name". When you update it, the system sends you an email saying "Hello [Display Name]". The web page itself never shows your name.

The Question: How do you test for SSTI here?

The "Hired" Answer:

"This is Blind SSTI. I cannot see the output on the screen.

1. I would try payloads that cause a time delay (e.g., `{% import time %}{{ time.sleep(5) }}` if allowed).
    
2. I would try to break the template syntax (e.g., `{{`) to see if the email fails to arrive (indicating a server-side error/crash).
    
3. I would try to inject a payload that triggers an out-of-band interaction (DNS/HTTP request) to my Burp Collaborator server."
    

### 🎭 Scenario 2: The WAF Block

Context: You confirmed SSTI with {{7*7}}, but when you try to inject __class__ or subprocess, the WAF blocks you (403 Forbidden).

The Question: How do you bypass this?

The "Hired" Answer:

"I would try syntax obfuscation techniques allowed by the language:

1. **String Concatenation:** `__cl` + `ass__` inside the template syntax (e.g., `request['__cl'+'ass__']`).
    
2. **Hex/Unicode Encoding:** Encoding the underscore characters.
    
3. **Alternative Access:** Using `request.args` to pass the blocked keywords via a GET parameter (e.g., `{{ request[request.args.p] }}` where `?p=__class__`). This way, the malicious keyword is in the query string, not the template payload."
    

### 🎭 Scenario 3: The "Limited" User Input

Context: A website allows you to upload a custom HTML template for your profile page, but it claims to "sanitize" inputs by removing <script> tags.

The Question: Is this secure against SSTI?

The "Hired" Answer:

"Likely not. Removing <script> tags prevents XSS, but SSTI doesn't use script tags; it uses template delimiters like {{ }} or <% %>. If the application renders my uploaded HTML file using a template engine, I can inject {{ system('ls') }} (for PHP/Smarty) or similar. The sanitization for XSS is irrelevant for SSTI."

### 🎭 Scenario 4: The "PDF Report"

Context: An invoice application takes your name and address and generates a PDF report. You suspect the PDF generation library uses a template engine under the hood.

The Question: What is the specific risk here, and how do you test it?

The "Hired" Answer:

"Many PDF generators (like WeasyPrint or wkhtmltopdf) render HTML/CSS templates first. If my input is injected into that HTML template:

1. **Risk:** SSTI leading to RCE on the PDF generation server. Also, SSRF (fetching internal files to print in the PDF) and LFI (Local File Inclusion).
    
2. **Test:** I would try injecting template syntax like `{{ 7*7 }}` into the name field and check if the generated PDF shows '49'. If so, I would escalate to reading `/etc/passwd` via the template."
    

### 🎭 Scenario 5: The "Cloud" Environment

Context: You have achieved RCE via SSTI on a web server running in AWS. The server is hardened, and you cannot easily upgrade to a persistent shell.

The Question: What is your immediate next move to demonstrate maximum impact?

The "Hired" Answer:

"I would leverage the SSTI to perform SSRF (Server-Side Request Forgery) to hit the cloud metadata service.

1. **Payload:** I would use `curl` or `urllib` (via Python SSTI) to fetch `http://169.254.169.254/latest/meta-data/iam/security-credentials/`.
    
2. **Goal:** Steal the temporary IAM credentials (Access Key, Secret Key, Token) associated with the EC2 instance.
    
3. **Impact:** This allows me to persist access via the AWS API, potentially escalating privileges within the entire cloud infrastructure, bypassing the hardened server shell."

## 🛑 Summary of Part 1

1. **Concept:** SSTI occurs when user input is concatenated into a template, allowing the engine to execute it as code.
    
2. **Impact:** Unlike XSS, SSTI leads to Server-Side RCE.
    
3. **Attack:** We identify the engine using math (`7*7`) and use object introspection (MRO chains) to escape the application and run shell commands.
